# Второй этап: данные и админка

Подготовлено поверх коммита `72333e20` из `feature/01-setup`.
Изменения можно изучать, пока первый этап находится на проверке. После ответа
куратора нужно учесть его правки и сверить пакет с принятой версией.

## Перенос

Скачайте `stage-02.patch` в Ubuntu, например в `~/Downloads/`.
После принятия первого этапа обновите master и создайте ветки второго этапа:

```bash
cd ~/python_django_diploma
git status
git fetch origin
git switch master
git pull --ff-only
git switch -c release/02-models
git switch -c feature/02-models
git apply --check ~/Downloads/stage-02.patch
git apply ~/Downloads/stage-02.patch
poetry install --no-root
poetry check --lock
poetry run python manage.py check
```

Если `git apply --check` сообщает конфликт, остановитесь: патч нужно сверить
с замечаниями куратора. Эти команды не создают коммит и не отправляют изменения.

## База

До миграций проверьте состояние имеющейся базы:

```bash
poetry run python manage.py showmigrations
```

Если на первом этапе миграции не применялись и рабочих данных нет, можно
переименовать `db.sqlite3` в резервную копию, затем выполнить:

```bash
poetry run python manage.py migrate
poetry run python manage.py changepassword admin
poetry run python manage.py loaddata demo
poetry run python manage.py test catalog
poetry run python manage.py runserver 127.0.0.1:8000
```

При наличии ценных данных сначала нужен отдельный перенос в новую модель
пользователя. В пакет не входят `.env`, пароли администратора и база данных.

## Проверка и сдача

В админке можно архивировать и разархивировать выбранные категории, товары и
учётные записи. Для пользователя разархивирование снимает архивный статус, но
не включает вход обратно автоматически: администратор отдельно проверяет
учётную запись и при необходимости включает её. Также в админке можно
редактировать каталог, цены и остатки продавцов, изображения,
характеристики, скидки и стоимость доставки. Заказы доступны для просмотра
и мягкого удаления. Состав заказа защищён от ручного изменения.

Проверьте подтверждение удаления и сохранность связанных записей, отказ во
входе удалённому пользователю, ошибки на неверный телефон, повторный email,
третий уровень категорий, отрицательную цену и некорректное изображение.

После своей проверки пользователь сам делает коммит и push. Тематический MR
направляется в `release/02-models`, затем после код-ревью готовится релизный MR
в `master`. Тематическую ветку сохраняем при сдаче этапа.

API, корзина, оформление заказа и очередь оплаты относятся к следующим этапам.
Демонстрационный оплаченный заказ в фикстуре служит для просмотра данных;
платёжная обработка этим этапом не реализована.

## Сверка

Модель пользователя задана до первых рабочих миграций согласно документации:
https://docs.djangoproject.com/en/5.2/topics/auth/customizing/#using-a-custom-user-model-when-starting-a-project
Миграции данных используют исторические модели и RunPython с обратной функцией:
https://docs.djangoproject.com/en/5.2/topics/migrations/#data-migrations

Сохраняем Poetry единственным способом управления зависимостями.
`DJANGO_DEBUG=1` предназначен для разработки; production-развёртывание и
обслуживание файлов без DEBUG будут проверены на этапе развёртывания.
Точных старых замечаний куратора о валидации в доступном контексте нет —
их нужно сопоставить с реализацией, когда они будут предоставлены.
